# P2 待决事项的细节（给醒来后的讨论用）

这份文件补 `docs/P2-STATUS.md` 里那三条待决事项的来龙去脉，每条都写清楚：卡在哪、有几种选法、各自的代价。

## 1. 启停要不要走到 plan/apply 里（§21.5）

**现状**：`o824 start` / `stop` 是独立的子命令，直接调 `o824-webform`。这是**偏离规范**的——§21.5 明确写着：

> 协议层没有 `o824.start` / `o824.stop` 这样的方法：`start` / `stop` 是 `plan` 的 `action`，走同一套 plan/apply 与确认流程。

**为什么不趁夜里改**：这不只是加两个字符串。`o824-plan` 的核心契约是"由 findings 生成修复步骤"；加上动作驱动意味着它要同时支持"由 action 生成步骤"，而 `apply` 要多两个步骤类型（`start-web` / `stop-web`）。协议面、planner 契约、CLI 三条路径都动，属于该在你醒着的时候定的改动。

**两种收法**：

- **A（推荐）**：`o824.plan` 接受 `action: "repair"|"start"|"stop"`（默认 `repair`，向后兼容），`apply` 执行；CLI 的 `start`/`stop` 改成"建计划 + 立即 apply"（显式命令本身就是确认）。好处是**只有一条路径**，符合 §21.5。代价：改动约 300 行 + 测试，且 `desktop`/`tui` 的动作要以 `E_KIND_UNSUPPORTED` 拒绝（这个错误码 §21.5 里就有）。
- **B**：保持独立子命令，把规范那句改成"CLI 可直接启停，协议层不提供"。好处是零改动；代价是第三方 UI 想启停就得自己 spawn，而"谁 spawn 谁才有管道句柄"这条授权链就断了。

## 2. desktop 形态的 start/stop 语义

**现状**：只做了 web。`desktop` 形态的"启动"是拉起那个 GUI，而 `desktop` profile **同时只能跑一个实例**（DSH 自己独占）。

**选法**：

- **A**：`start` 只在"没有实例在跑"时启动，在跑就报告"已经在跑（pid N）"并以 0 退出。最符合工具直觉。
- **B**：`start` 一律拒绝，只提供 `status`/`stop`。安全但半边功能。
- **C**：完全不做（`E_KIND_UNSUPPORTED`），桌面端交给用户双击。

我倾向 A，但它有一个副作用要你确认：`o824 start` 会**真的打开一个窗口**，在无人值守的场合（CI、脚本）里这是意外的。

## 附：这一夜的两次真实教训

两个 bug 都不是读代码发现的，是**重复跑测试**（12 次里挂 1 次）暴露的：

1. `stop` 在 `TerminateProcess` 返回时就报"已停"，而进程还没退完。
2. 记录里的 `started_at` 是给人看的时间戳，身份检查却拿"当场读的创建时间"和它自己比——等于没检查。

第二个尤其值得记：它看起来像一道安全闸门，实际上什么都没拦。现在两处都有测试，且那个检查会拒绝"没有创建时间的记录"。
